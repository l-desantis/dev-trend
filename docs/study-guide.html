1. The 60-second model

DevTrend is a staged pipeline monolith driven by a scheduler. One FastAPI process hosts: the APScheduler job store, the Telegram bot (polling), and a /health endpoint. There are no microservices, no queue, no workers. Everything is async Python over PostgreSQL 16 (async SQLAlchemy + Alembic).

The governing design rule: the LLM is used only where it is the best available tool; everything that must be reproducible is deterministic code.
  • LLM does: unstructured text → structured PainPoint records (strict Pydantic schema), and naming/summarising clusters.
  • Deterministic code does: embedding, identity resolution, clustering, validation, scoring, lifecycle, ranking.
Consequence: aggregation and ranking are reproducible run-to-run, instead of being re-litigated by a model every night.

Startup order inside lifespan() — this is the exam question:

  1. _configure_logging() — structlog + stdlib unified under one ProcessorFormatter; noisy loggers (httpx, telegram, uvicorn.access) pinned to WARNING. httpx logs would otherwise leak the bot token in URLs.
  2. check_db_reachable() — fail fast if Postgres is down.
  3. sync_categories_from_yaml(data/categories.yaml) — categories are config, not data entry.
  4. Build httpx.AsyncClient + ConnectorRunRegistry + the 3 always-on connectors (GitHub, HN, Reddit).
  5. If TELEGRAM_BOT_TOKEN set: build bot app, initialize() → start() → register the 8 slash commands → updater.start_polling().
  6. If BACKFILL_ON_EMPTY=true and source_items is empty: run bulk_backfill() synchronously before the scheduler starts.
  7. build_scheduler(...) then scheduler.start().
  8. yield … on shutdown: scheduler.shutdown(wait=False), stop updater/bot, close HTTP client.
Trap: the scheduler is in-process and in-memory. A restart loses any pending/misfired job state; misfire_grace_time only covers a running process that was busy. Scaling to 2 app replicas would double-run every job — there is no distributed lock.

4. The scheduler — app/ingestion/scheduler.py

build_scheduler(connectors, registry, settings, *, bot=None) returns a single AsyncIOScheduler and registers every job. Three structural points:

  • Every job is defensive. Each wraps its body in try/except Exception and logs; a crashing job never kills the scheduler or the process.
  • Ingestion jobs are also time-boxed via asyncio.wait_for(..., settings.ingestion_job_timeout_s) (180 s default; ×4 for Play Store, ×2 for iOS). On timeout the ConnectorRunRegistry is marked with an error so /sources in the bot shows it.
  • Imports are deferred inside the job bodies — heavy modules (numpy, hdbscan, LLM adapters) are not imported at scheduler-build time, which keeps startup fast and avoids import cycles.

Why this ordering matters

02:00  playstore ingest ─┐
02:30  app discovery (Mon)│ fresh SourceItems land BEFORE the pipeline
03:00  pruning (Sun)      │ old rows gone before we spend LLM tokens on them
03:30  pipeline ──────────┘ extract→embed→resolve→cluster→label
04:00  recluster (Sun)      runs AFTER the pipeline so it sees today's candidates
04:15  scoring              needs today's candidates + pain points to exist
08:00  digest               needs today's scores + lifecycle states

The comment in the Play Store job states the intent explicitly: it runs before the pipeline deliberately so same-day reviews make the same day's digest. Any schedule change must keep this ingest → pipeline → score → deliver chain in order.

APScheduler flags, in plain English. max_instances=1: never run two copies of the same job concurrently. coalesce=True: if several fire times were missed, run once, not N times. misfire_grace_time=N: if the job is late by more than N seconds, skip it instead of running stale. Ingestion uses 300 s (a missed 6-hour tick is cheap to skip); pipeline/scoring/digest use 3600 s (losing a day's run is expensive, so allow an hour of slack).

5. Pipeline stages 1–5 — app/pipeline/orchestrator.py

run_pipeline() is deliberately boring: five sequential awaits, each in its own async with session_factory() as session, each returning a typed *Report dataclass aggregated into PipelineReport. Per-stage sessions mean a late failure doesn't roll back earlier stages' work.

#StageInput → outputKey knob
1run_extractionsource_items (state=pending) → pain_pointsEXTRACTION_BATCH_SIZE=20, optional since/limit
2run_embeddingpain points without embedding → vector + embedding_modelEMBEDDING_BATCH_SIZE=64
3run_identity_resolutionunattached pain points → candidate_id setIDENTITY_RESOLUTION_THRESHOLD=0.65
4run_clusteringstill-unattached pain points → new candidatesCLUSTERING_MIN_CLUSTER_SIZE=3
5run_labellingcandidates with labeller_model IS NULL → namedLLM

Stage 3 — identity resolution (the most load-bearing stage)

active candidates WHERE centroid IS NOT NULL
      │ group by embedding_model          ← prevents 768-d vs 1024-d vs 1536-d mixing
      ▼
EmbeddingIndex per model  (built ONCE per model: O(M), not O(N·M))
      │
unattached pain points WHERE embedding IS NOT NULL
      │ nearest centroid in the SAME embedding_model bucket
      ▼
cosine ≥ threshold (0.65) ? attach + refresh centroid/last_evidence_at : leave for stage 4

This stage is why the system doesn't re-discover the same theme every night. If it under-attaches you get duplicate candidates daily; if it over-attaches you get a "monster candidate" absorbing everything. Both failure modes are listed in the README's diagnostics section, with scripts/diagnose_attachment.py as the instrument.

The 0.82 → 0.65 story. The threshold was originally tuned for Ollama nomic-embed-text (768-d). Under NVIDIA nv-embedqa-e5-v5 (1024-d) the true-positive band sits at p50 ≈ 0.704 with a novel-leftover ceiling of 0.622, so 0.82 was unreachable and nothing ever attached. 0.65 sits between those two numbers. The threshold is a property of the embedding model, not of the problem domain.

Stage 4 — clustering

_cluster_labels() tries hdbscan.HDBSCAN(min_cluster_size, metric="euclidean") and falls back to AgglomerativeClustering(n_clusters=n//min_cluster_size, metric="cosine", linkage="average") on ImportError, post-filtering clusters smaller than min_cluster_size to noise (-1). hdbscan is intentionally not in pyproject.toml — the native binary is unreliable on WSL2, so the import-and-fallback is the safety net.

Known inconsistency: clustering uses Euclidean, identity resolution uses cosine. On normalised vectors these are monotonically related, but the mismatch is by omission, not design.

6. Validation, scoring & lifecycle

a) GitHub validation — app/pipeline/validation.py

Searches GitHub for repos matching candidate keywords (LLM-extracted) and writes a candidate_validations row with signal_type="composite" and metadata_json = {repo_count, max_stars}.

b) Scoring — app/scoring/

Gate first: only is_archived = false AND specificity > SPECIFICITY_GATE (2) candidates are scored. The job is idempotent per as_of date — it deletes that day's existing candidate_score_history rows before inserting, so a re-run doesn't double-count.

DimensionWeightRaw computationNormalisation
momentum0.30rolling_slope() of daily pain-point counts over 7 dayspercentile
frequency0.25count of pain points in the last 30 dayspercentile
validation0.20validation_curve(repo_count, max_stars)already 0–100
source_diversity0.15distinct source buckets (reddit:<sub>, playstore:<app_id>, else source_type)percentile
specificity0.10specificity × 20 → 20–100already 0–100

The validation curve is non-monotonic on purpose — more GitHub repos is not linearly worse:

repo_count == 0                       → None   (NO SIGNAL, not "novel";
                                                 likely a search miss →
                                                 remaining weights renormalised)
repo_count ≤ 5  and max_stars ≤ 5000  → 90   someone tried it, nobody won → best
repo_count ≤ 20 and max_stars ≤ 20000 → 70   real market, beatable
otherwise                             → 30   crowded / solved

Source diversity is bucketed, not typed. Ten complaints from ten different subreddits score higher than ten from r/startups alone — the bucket key is reddit:<subreddit>, not "reddit". Same for individual Play Store apps. This is the anti-echo-chamber mechanism.

Percentile normalisation (normalize_with_neutral_fallback) means scores are relative to the current candidate population, with a neutral value substituted when the population is too small for percentiles to mean anything. A score is a rank, not an absolute.

c) Lifecycle — app/pipeline/lifecycle.py

derive_lifecycle_state() reads the normalised momentum and frequency from the latest score row and returns one of emerging | hot | saturated | dormant | None:

evidence_ref = candidate.last_evidence_at or candidate.created_at   ← the bug fix
last_pp_age  = (scored_at - evidence_ref).days
age_days     = (scored_at - created_at).days

if last_pp_age >= 14                                  → "dormant"   (checked FIRST)
if momentum ≥ 60 and frequency < 30 and age_days < 14 → "emerging"
if momentum ≥ 60 and frequency ≥ 30                   → "hot"
if frequency ≥ 70 and momentum < 30                   → "saturated"
otherwise                                             → None (unclassified)
The "immortal hot" bug. When last_evidence_at was NULL the age computed as 0, so evidence-less candidates could never reach dormant and sat at hot forever. The fallback to created_at fixes it: a candidate's freshest signal is its birth, not "today".

Only changed states produce a lifecycle_events row. A transition to None is recorded but never alerted. Real transitions are returned sorted by score DESC, so emit_lifecycle_alerts() can truncate at MAX_ALERTS_PER_DAY = 3 and keep the best ones.

8. LLM & embedding layer — app/llm/

Two parallel abstractions — LLMAdapter (chat/extraction/labelling) and EmbeddingAdapter — each with four implementations behind make_llm_adapter(settings) / make_embedding_adapter(settings). The provider is chosen by LLM_PROVIDER and EMBEDDING_PROVIDER, which are independent.

ProviderChat modelEmbedding model (dims)Structured-output strategy
ollamaqwen2.5nomic-embed-text (768)JSON mode → Pydantic validation
nimmeta/llama-3.1-70b-instructnvidia/nv-embedqa-e5-v5 (1024)OpenAI-compatible; rate limiter at 40 rpm
openaigpt-4.1-nanotext-embedding-3-small (1536)native parse API with a Pydantic response model
mock——Deterministic stub; the test suite runs offline

Structured output is enforced, not hoped for: either the provider's schema-constrained parse or JSON mode followed by Pydantic validation. Prompts live in app/llm/prompts.py as templates, not inline f-strings, so they are diffable and testable.

Embedding buckets are a one-way door. Each provider's vectors live in their own embedding_model bucket and cross-provider identity resolution is disabled by design (different dimensionality, different geometry). Switching providers mid-life means new pain points never match old candidates — they fork into a parallel universe of duplicates. Pick one provider per deployment; a one-off re-embed script is a known follow-up, not a shipped feature.

9. Telegram delivery — app/bot/

Two push paths and one pull path.

  • Daily digest (08:00) — run_digest_job() takes the top DIGEST_TOP_N (3) candidates, generates a brief (LLM headline + summary + up to BRIEF_MAX_EVIDENCE_ITEMS=5 evidence items), persists candidate_briefs, and sends a message with 👍/👎 inline buttons.
  • Lifecycle alerts (04:15, tail of the scoring job) — emit_lifecycle_alerts() on the transitions list, capped at MAX_ALERTS_PER_DAY (3), highest score first.
  • Commands (pull) — /start, /help, /opportunities, /opportunity <id>, /categories, /category <slug>, /emerging, /sources. /sources reads the in-memory ConnectorRunRegistry, which is why it reflects the current process only.

Access is restricted by TELEGRAM_ALLOWED_CHAT_IDS (middleware). Messages are chunked against the 4096-character Telegram limit (TELEGRAM_MAX_MESSAGE_CHARS). Feedback (candidate_feedback) is captured today as a training/calibration signal — it does not yet feed back into scoring weights.

Production

  • Single Hetzner CX22 VPS, deployed on every push to main.
  • Five GitHub Actions workflows: ci, build-and-push, deploy (health-gated, auto-rollback), rollback (manual, by SHA), prune-ghcr (keeps last 10 sha-* + latest).

12. Traps, gotchas & open gaps

  • No labelled evaluation set. Tests prove the pipeline behaves, not that extraction or clustering is good. No precision/recall for pain-point extraction or cluster coherence. Self-declared biggest gap.
  • Metric mismatch: clustering Euclidean vs identity resolution cosine.
  • HDBSCAN is untuned — only min_cluster_size is passed; min_samples and cluster_selection_method are defaults. It is also not a declared dependency.
  • Single-instance assumption — in-memory scheduler, in-memory ConnectorRunRegistry, bot long-polling. Two replicas = duplicate jobs and duplicate Telegram sends.
  • Play Store scraping is a community library over a DOM that can change silently, and may violate Google's ToS. The pinned smoke-check script is the early-warning system.
  • Reddit RSS caps history, so backfill depth per subreddit is bounded regardless of --history-days.
  • Scoring weights are placeholders awaiting enough 👍/👎 feedback to calibrate; feedback is currently collected but not consumed.
  • docs/architecture.md is an empty file. This guide and the README are the real architecture docs; devtrend-project-document.md and docs/superpowers/ hold the design history.

  2. A pain point exists with an embedding but candidate_id IS NULL after the pipeline ran. Name the two stages that could have left it there and why.

  4. Why does validation_curve() return None rather than 100 for repo_count == 0?
